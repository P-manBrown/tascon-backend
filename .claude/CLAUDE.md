# TASCON（バックエンド）

TASCONのバックエンド個人開発用リポジトリ。
TASCON = タスク管理・テンプレート共有Webアプリ。

## コーディング方針（全般）

LLMコーディングでの典型的なミスを減らすための行動指針。速度より慎重さを優先する設計→些細なタスクでは判断で調整可。

### 1. 実装前に考える

仮定を明示。曖昧なら質問し、黙って進めない。

- 前提は明示的に述べる。不明なら質問
- 複数解釈ある場合→選択肢を提示（黙って一つ選ばない）
- よりシンプルな代替案があれば提案。過剰な要求には異議を
- 不明点があれば実装を止め、何が不明か明言してから質問

### 2. シンプル最優先

要求を満たす最小限のコードのみ実装。投機的な実装はしない。

- 依頼範囲外の機能追加禁止
- 単発利用コードの抽象化禁止
- 依頼されていない柔軟性・設定可能性の追加禁止
- 発生しないシナリオへのエラーハンドリング禁止
- 200行で書けそうなものが50行で済むなら書き直す
- 判断基準:「シニアエンジニアが見て過剰実装と言うか」→Yesなら簡略化

### 3. 外科的変更

必要な箇所のみ変更。自分が生んだ問題のみ片付ける。

- 既存コード変更時、無関係なコード・コメント・フォーマットは「改善」しない
- 壊れていないコードのリファクタ禁止
- 既存スタイルに合わせる（自分の好みと違っても）
- 無関係な不要コードを発見した場合→削除せず言及のみ
- 自分の変更で発生した不要import/変数/関数→削除する
- 元々存在した不要コードは依頼がない限り削除しない
- 基準: 変更した行すべてがユーザーの依頼に直接紐づくか

### 4. ゴール駆動実行

成功基準を定義し、検証されるまで作業を続ける。

- 「バリデーション追加」→「不正値のテストを書き、パスさせる」
- 「バグ修正」→「再現テストを書き、パスさせる」
- 「Xをリファクタ」→「変更前後でテストが通ることを確認」
- 複数ステップの作業→簡潔な計画を提示: `1. [ステップ] → 検証: [確認方法]`
- 成功基準が強いほど自律的に作業継続可能。「うまく動くようにして」等の弱い基準は都度確認が必要
