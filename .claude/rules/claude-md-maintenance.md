# Claude関連ドキュメント運用方針

## 置き場所判断

- 常に必要な文脈（プロジェクト全体の前提・振る舞い方針）→ CLAUDE.md
- 特定ファイルパスを触るときだけ必要 → `.claude/rules/*.md`
- 特定タスク遂行時のみ必要な手順（コミット作成・リリース手順等、パスに紐付かない） → `.claude/skills/*/SKILL.md`
- 個人の作業スタイル・ツール利用方針など、プロジェクト全体・将来のセッションに影響しない内容 → `.claude/memory/`
- プロジェクト全体のルールとして今後も参照されるべき内容を`.claude/CLAUDE.md`、`.claude/rules/*.md`、`claude/skills/*/SKILL.md`へ記述する

## 実践

- 強調語（`IMPORTANT`/`YOU MUST`等）は最後の手段。乱用すると全体的に効果が弱まる。本当に外せないルールにのみ使う
- `CLAUDE.md`が200行超過時→`.claude/rules/*.md`への切り出しを検討

## CLAUDE.md・AGENTS.md・rules・skillsの作成・変更時の必須手順

次のファイルを作成、または1行でも変更したら、コミット前に**その場で**次を実施する。

- `.claude/CLAUDE.md`
- `AGENTS.md`
- `.claude/rules/`配下のファイル
- `.claude/skills/`配下のファイル

1. 変更後に期待する行動を1点決め、それを引き出す具体的プロンプトを1つ書き出す。プロンプトは、本番でそのルール・skillが読み込まれる場面（関係するファイルの編集、該当する作業の依頼等）にし、ルール・skillの名前や手順の有無を直接問わない
   - 手順1の場面を`rule-tester`で作れないとき（`paths`が`rule-tester`の読めない場所だけを指すルール等）は、ダミーのファイル等で場面を作る。`.claude/plans/`配下を`paths`に持つルールは、`.claude/plans/rule-test-fixture.md`に中身のないダミーのplanを置き、プロンプトでそれを読むよう指示する。ダミーはテストの後に消す。場面を作れないまま変更を残さない
2. テスト対象のファイル以外の未コミット変更を`git stash push -u -- . ':(exclude)<テスト対象のファイル>'`で退避し、続けてテスト対象の未コミット変更を`git stash push -u -- <テスト対象のファイル>`で退避する。`git stash push`が`No local changes to save`で何も退避しなかったときは、対応する`git stash pop`をしない。手順5まで戻さず、退避中は他の作業をしない
3. テスト対象の変更、またはその変更の意図を書いた記録（plan等）をコミット済みなら、それらを最初に含むコミットの1つ前へ`git switch --detach <コミット>^`で移る。移ったら、最初に`rule-tester`を起動する前に、`git restore --source=<元のブランチ> --worktree -- .claude/agents/rule-tester.md .claude/hooks/rule-tester-guard.sh`で今の`rule-tester`の定義とガードを作業ツリーへ置き、`rule-tester`に定義の指示文を答えさせて、今の定義で動いていることを確かめる。Agentツールで`rule-tester`を`isolation`なしで起動して、そのプロンプトのみを与える（変更前の挙動）。`isolation: "worktree"`は使わない
4. 手順3で移ったなら、置いた2つのファイルを`git restore --worktree -- <ファイル>`で戻す（移った先にないファイルは削除する）。そのうえで`git switch -`で元のブランチへ戻る。手順2でテスト対象の変更を退避したなら`git stash pop`で戻す。同じプロンプトで`rule-tester`を起動する（変更後の挙動）
5. `git stash pop`で手順2の最初に退避した変更を戻す。テストの結果をplanの`検証結果`へ記録するのと、変更内容を表すブランチを作るのは、ここまで終えた後にする
6. 手順1の行動が、変更前になく変更後にあるかだけで判定する。言い回し・順番・変更と関係のない提案の差は判定に使わない
   - 変更後にも現れない、または変更前にも現れる→ノイズ。その変更をその場で取り消し、同一コミットに含めない
   - 指示を足さず、人が読んで対象・範囲を分かりやすくするだけの書き換えは、行動が変わらなくても残してよい

## SKILL.md/rules執筆時の原則

- 日本語で記述する
- 理由・経緯は書かない。書く場所は`.claude/plans/`のDecision Log。SKILL.md/rulesは「今の正しい手順」だけに絞る
- 動作を確認していない手順は加えず、未確認であることをplanに記録する
- 他skillの実装詳細（具体的なコマンド・パス等）はコピーせず、そのskill名への参照に留める。実装は1箇所に集約し、変更時の追従漏れを防ぐ
- 具体例の列挙・具体的な実装手法（コード片・コマンド等）ではなく、一般原則を記述する
  - 誤ると復旧が困難な操作の手順は、例外として具体的なコマンド・オプションを記述する

## 新規skill設計時の原則

- 際限なく増える可能性のあるデータを記録する仕組みは、最初から1件1ファイルにする。単一ファイルへの追記型は肥大化する
- サブエージェント等への委任を含む設計では、情報を取得できる側が委任時にそのまま渡す。委任先に同じ情報を再取得させない

## 変更時の確認

- ルール・用語（子タスク名、判定基準等）を変更したら、`grep`で言及箇所を全ファイルから洗い出し、まとめて更新する
