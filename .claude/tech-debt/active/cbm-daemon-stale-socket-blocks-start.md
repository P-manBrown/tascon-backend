# codebase-memory-mcpのdaemonが残したソケット等の残骸で、daemonもMCPも起動できなくなる
- **Status:** Open
- **Priority:** Medium
- **Category:** Infrastructure
- **Area:** `.devcontainer/devcontainer.json`（`codebase-memory-mcp` feature）、`/tmp/cbm-daemon-1000/`
- **Detected:** 2026-10-18
- **Todoist Task ID:** `6hpQWVwp8MHGXG5q`
- **Description:** codebase-memory-mcp 0.12.1のdaemonプロセスが終了した後、`/tmp/cbm-daemon-1000/`に`cbm-<hash>.sock`・`cbm-<hash>.sock.identity`・`cbm-<hash>.anc`が残ることがある。残っていると、CLIはプロセスの生存を確認せずに起動済み・起動中と扱う。そのため`codebase-memory-mcp daemon start`もMCPのstdio起動も`CBM daemon could not start within 30000 ms`で失敗する（`.sock`が残っている場合は30秒の接続待ちでタイムアウトし、`.anc`が残っている場合は数秒で同じエラーになる）。2026-10-18に発生し、2026-10-20にも同じ状態（daemonプロセスなし、`.sock`・`.anc`あり、Claude Codeでは`codebase-memory-mcp (CONNECTION_CLOSED)`）を確認した。復旧方法は次のとおり。`ps`でdaemon（`--cbm-daemon-internal`）が動いていないことを確認し、`.sock`・`.sock.identity`・`.anc`を退避または削除してから`codebase-memory-mcp daemon start`を実行し、Claude Codeでは`/mcp`で再接続する。`.lock`ファイル類は残してよい。
- **Impact:** セッション開始時からcodebase-memoryのMCPツールが使えず、hookによるグラフ情報の差し込みも止まる。原因が残骸ファイルだとは分かりにくく、発生するたびに手作業での調査と復旧が必要になる。
- **Proposed Resolution:** このリポジトリ内の仕組みで、起動前に残骸を検知して片付ける。たとえば、Dev Containerの`postStartCommand`かSessionStartフックで、daemonプロセスが存在しないのに`.sock`・`.anc`が残っている場合にだけ、それらを退避してから`daemon start`する。
